# ClipFlow｜飞书多维表领取与回填工作流（配置模板，待绑定）

> 状态：**WORKFLOW_SPEC_READY / TABLE_BINDING_PENDING**。此文档不含真实 `app_token`、`table_id`、`record_id`、凭据或用户视频。用户明确将在稍后固定多维表页面、未完成标记和成品单元格；在完成绑定与针对目标记录的读写能力验收之前，**不能声称真实表格任务已经执行**。

## 一、启动前的强制自查（每个新AI窗口独立执行）

1. 读取本仓库最新版 `AGENTS.md`、`README.md`、本文件和已绑定的表格字段映射。优先复用已安装的程序/CLI、已连接的官方飞书多维表MCP或API；不规定必须使用某一种通道。**不从聊天窗口寻找原视频，也不要求用户再次上传素材**。
2. 读取连接状态及授权范围（例如 `bitable_connection_status`、`bitable_attachment_permissions`，或等效的CLI/API只读检查）。核对当前运行环境实际拥有目标表的**记录读取、附件实际字节下载、成品附件上传与目标记录更新**能力；有OAuth scope、显示网页链接或“连接成功”本身并不能证明该记录可写。只读检查不得产生测试附件或乱写生产行。
3. 使用用户固定的 `app_token`、`table_id`、`view_id`（如有）读取真实表结构及至少一条目标记录；校验 `备注`、`处理阶段`、`待处理素材`、`成品` 等**由用户实际指定的字段**存在且类型匹配。`成品`应为**多附件字段**，能够在同一记录单元格收纳多个文件，不要将多项文件塞进一个文本字符串或覆盖其他记录。
4. 确认下载接口可以读取选中记录的附件**真实字节**，大附件需要分块下载并核对长度与SHA256。上传前确认**该文件格式**存在真实可用的上传渠道：视频/ZIP的现有飞书MCP可能可用，但`.txt`必须另外核验是否有通用附件上传能力；没有TXT专用/通用上传能力就**HOLD该记录**，不可把TXT偷偷压入ZIP或谎称已全量交付。CLI/API/MCP哪条真实可用便用哪条，且只能向被批准的表/记录/字段写入。
5. 未绑定具体表格、找不到字段、没有实际读写权限、跨账号连接缺失、附件下载未获得完整字节或TXT不能上传时，报 `BITABLE_ACCESS_HOLD` 并说明缺的能力。不能伪造下载、上传或任务完成，不自行创建/修改业务表结构、不自行申请扩大权限。

## 二、记录模型（所有名称以用户随后固定的真实字段为准）

| 角色 | 暂定字段名 | 约束 |
| --- | --- | --- |
| 任务范围 | 多维表 app_token / table_id / 可选 view_id | 必须来自用户明确指定的固定页面或配置；不可猜邻近表 |
| 未完成标记 | `备注` | 默认采用**字段值去除首尾空白后严格等于 `未完成`**；若用户指定匹配其他文本，再改配置 |
| 阶段路由 | `处理阶段` | `第一阶段`＝单条对标原视频；`第二阶段`＝待合成新片段及必要参考资料；无法判断则HOLD |
| 输入附件 | `待处理素材` | 记录本身的附件；必须核验归属、来源与顺序；第二阶段允许多个MP4或已明确的片段ZIP |
| 完成附件 | `成品` | 同一**原记录**的指定多附件单元格；第一阶段需包含完整ZIP与单独的`文案.txt`，第二阶段需包含最终MP4、验收JSON和实际要求的其他文件 |
| 状态/并发控制 | 用户指定的任务状态或备注字段（待定） | 能原子认领则先认领；无安全认领机制时单窗口运行，不与其他实例抢同一记录；不能仅靠本地状态去重 |

> 这里的 `备注`、`待处理素材`、`成品`、`处理阶段` 是**待绑定的逻辑名称**，不是对任何真实表字段的断言。一个“固定单元格”解释为**每条待办记录中指定的成品附件列**；若用户希望所有任务都写同一个跨记录单元格，必须先再次明确，因为那样无法可靠追溯或避免覆盖。

## 三、单条任务执行（两阶段共用）

1. 按固定视图/表筛选 `备注 = 未完成`，**分页遍历并核实待处理记录**。默认每次按稳定顺序只领取一条，避免重复与并发抢任务。若同一记录已有完整已验证交付，则先比对附件名称、数量、SHA/记录审计，不能再无条件重复上传。
2. 读取选中记录的 `处理阶段` 与 `待处理素材`。按记录ID和字段归属下载视频/ZIP/音频/参考素材；下载必须得到实际字节及尺寸/哈希校验。失败时不要改成已完成。
3. **第一阶段**使用 `clipflow reference`：严格(3,8]秒、完整句尾、画面镜头优选、每段开头10帧文字最少的同号JPG、原片SRT行尾无标点、逐段台词MD、样张/manifest/CSV。正式交付**两个独立文件**：`ClipFlow_完整交付.zip` 和 `文案.txt`；TXT仅含原始识别的口播文字，逐条换行，不带标题、编号、时间码、Markdown或来源说明，**ZIP内禁止包含TXT**。
4. **第二阶段**使用 `clipflow assemble`：按有据可查的片段顺序完整拼接、模拟去灰通透，原声替换和烧字幕仅按记录中的显式授权开启。交付最终MP4和 `.report.json` 以及用户本任务明确要求的额外文件。不得擅自把第一阶段TXT当作第二阶段必须的输出。
5. 所有业务产物生成后先本地验收：可解码MP4、片段时长和镜头/语句规则、ZIP成员和CRC、TXT原文/非ZIP、manifest引用、哈希与文件大小。出现切分无解/HOLD或渲染失败，保留错误诊断，**不写“已完成”**。
6. 仅将目标记录需要的成品文件原字节上传至**同一条记录、同一个已绑定的成品附件字段**，必须追加且保留已有附件，不覆盖其他任务。大文件逐块按真实服务回执处理，幂等键由记录ID＋阶段＋产物SHA256组成；`uncertain`先检查远端任务，不盲目重复发送。若TXT或任何必交文件无法上传，整条记录保持未完成。
7. 上传后**重新读取该记录**并确认每个必交文件的名称/大小/可访问性，可能时重新下载对比SHA256。只有**所有**要求的成品已落到指定附件格且能读回，才将经用户批准的状态字段从未完成改为完成/写入完成时间。更新不能抹掉用户手写备注或旧附件。输出记录ID和交付清单，避免只有聊天下载链接。
8. 权限失效、未知表、同名字段冲突、多个待办争抢、下载/上传不完整、TXT不可上传或结果无法回读，则返回 `BITABLE_ACCESS_HOLD`／`BITABLE_DELIVERY_HOLD` 并记录实际证据；不假交付、不任意跳过后自动处理另一条记录。

## 四、绑定之前需要用户给定的内容（一次绑定，以后两种新窗口指令复用）

- 多维表 URL（含 `app_token`、`table_id` 或足以准确定位的真实链接）；若指定视图则同时给 `view_id`。
- 哪个字段是**未完成判据**、哪个是**输入附件**、哪个是**成品多附件列**；第一/第二阶段如何判定；若状态会写入，完成标记及可用的安全认领策略。
- 需要每次只做一条待办还是处理全部；默认**每次一条，避免抢占和长时自动批处理**。

这些是待绑定参数，不在公开GitHub写真实私有表ID、文件令牌或访问密钥。首次实际生产处理前，需用一条**获准的真实测试记录**完成下载→处理→上传→读回端到端验收；只有权限检查不能等同于视频工作流已经跑通。
