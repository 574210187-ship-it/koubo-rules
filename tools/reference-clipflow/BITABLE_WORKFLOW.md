**状态：STAGE1_ONLY / WORKFLOW_SPEC_READY / TABLE_BINDING_PENDING。**

用户于2026-10-28明确决定：本项目、本执行窗口与新执行窗口**只处理第一阶段（对标视频切分）**。第二阶段合并新视频不属于本程序的当前工作范围，禁止从任何飞书待办中领取第二阶段任务，禁止调用`clipflow assemble`。旧合并引擎仅作历史代码保留，CLI主动拒绝执行。不得因为看见旧版v0.4.6说明而恢复第二阶段。

## 1. 新执行窗口启动时必须自检（任何账号均适用）

1. 首先读当前正式 `README.md`、`AGENTS.md`、`BITABLE_WORKFLOW.md` 与 `PROMPT_FOR_CHATGPT.md`。当前唯一工作命令为 `clipflow reference`；`clipflow transcribe`仅为必要的第一阶段ASR辅助，`clipflow doctor`只做检查。**不要求用户向聊天发送视频**。
2. 自查当前环境已经由用户预先配置的飞书 CLI、MCP 或 API。任一条通路可用即可，但务必逐项验证：指定目标表记录只读访问、目标记录视频/附件真实字节下载、所有交付附件可上传到指定原记录的多附件字段、对该记录的读回与获准状态变更。OAuth scopes、网页登录状态和能列出表都不是字节下载/上传的成功证据。未经用户指定目标表，只能做连接状态的只读自查。
3. 只从用户明确给定的 `app_token`、`table_id`、可选 `view_id` 和字段绑定开始；不要凭相似名称、其他项目表或历史凭据猜测。核对真实的备注/未完成字段、原始对标视频输入附件字段、成品附件字段及（如需要）完成状态字段。`成品`应为同一条记录的多附件列，不能把多个文件写进文本格。
4. 必须实际确认当前附件上传路径支持 **ZIP和独立 `.txt` 两种完整文件**。本账号曾验证的专用MCP可上传视频/ZIP/GIF，不等于能上传TXT。如果TXT没有可用的通用CLI/API/MCP附件上传路径，停止并报 `BITABLE_ACCESS_HOLD`；不能把TXT压进ZIP、把文字塞进文本字段，或假称已交付。
5. 若缺目标表、权限、字段、真实下载字节、TXT上传能力、对方授权/文件格式支持或远端读回，必须记录具体证据并 HOLD。不得自行扩权、创建/修改陌生表、写测试附件或尝试处理第二阶段。

## 2. 第一阶段唯一任务记录（字段名称只是绑定模板）

| 用途 | 暂定名称 | 执行规则 |
| --- | --- | --- |
| 表格范围 | `app_token`、`table_id`、可选`view_id` | 来自用户固定的真实链接 |
| 待办筛选 | `备注` | 默认仅接受去首尾空白后**完全等于“未完成”**的记录；若用户另有规则以已批准映射为准 |
| 输入素材 | `待处理素材` | 对标**原始视频**的附件，不是第二阶段重做的片段 |
| 输出位置 | `成品` | **原记录**的多附件单元格；添加所有正式交付文件，不覆盖已有附件 |
| 完成状态 | 用户指定字段（待定） | 仅在所有交付远端读回通过并获准更新时写入；不擅自抹掉用户备注 |
| 阶段字段 | 不再必需 | 若真实表存在则仅处理明确属于第一阶段的行；第二阶段一律跳过/报告，不派发 |

“固定单元格”在本合同中指**每条已选中任务记录的固定成品列**。如果用户另指定跨行同一个单元格，需另行确认，不要擅自覆盖它。

## 3. 唯一处理闭环（默认每次一条）

1. 在用户固定视图/表中分页扫描备注为“未完成”的记录。默认按稳定顺序只领取**一条**。如果记录属于第二阶段或已有完整交付，不能重复处理；无可靠认领/锁时只允许单窗口串行处理，避免争抢。
2. 对选中记录确认 `record_id`、附件字段归属和来源；下载**真实完整字节**，大文件分块下载、核对文件大小及SHA256，确认视频可解码、有音频与足够的时长。拿到网页地址但没下载字节不算成功。
3. 只调用 `clipflow reference`，继承现行严格切分规则：每段实际时长**严格大于3秒且不超过8秒**，兼顾镜头转场且必须在完整句尾切分；无可行解生成`cut_conflict.json`并HOLD。001起C方案灰白水印、每段前10帧OCR文字最少的同号JPG、全文SRT每条显示行末去标点、逐段台词MD、manifest/CSV、字幕原帧样张与配置全部执行。无本地/授权云端ASR和无可信SRT时不可伪造文字结果。
4. 第一阶段必须形成 **两个相互独立的主交付文件**：`ClipFlow_完整交付.zip` 与 `文案.txt`。TXT是UTF-8无BOM纯口播识别原文，每条台词一行，不含标题、编号、时间码、Markdown或元数据；**ZIP中绝对禁止包含文案.txt**。ZIP包括所有编号MP4、对应JPG、SRT、MD、manifest/CSV和字幕样张等。
5. 本地验收全部文件非空、视频可解码、切分与截图边界合规、ZIP成员/CRC正确，TXT与ZIP分离。列出本次实际**对外交付的全部文件**，除ZIP+TXT之外，如果本次还会独立交付`captions.srt`、`segments_transcript.md`或兼容ZIP，也应按已批准的交付清单分别上传；中间缓存、临时转码文件、私密模型/凭据不上传。
6. 按 `record_id + 本阶段 + 文件SHA256` 形成每件幂等标识，把交付清单中的所有文件分别**追加**到该记录指定的多附件格，不覆盖原附件。遇到网络不确定状态，先查询任务和远端记录，不换key盲重试。ZIP、独立TXT或任一必交文件缺失都不算完成。
7. 上传完成后重新读取该记录，逐件确认名称、大小、可访问性，允许时再次下载核对SHA256。**只有完整交付清单都通过**，并且用户已定义可写完成字段/值，才能标记完成。状态更新不能抹掉手写备注或已有附件。
8. 找不到目标记录/缺权/真实附件下载失败/缺ASR/ZIP不合格/上传TXT不支持/输出不齐/远端读回失败时，按 `BITABLE_ACCESS_HOLD`、`BITABLE_PROCESS_HOLD` 或 `BITABLE_DELIVERY_HOLD` 记录原由；**保持未完成状态**，不跳到第二阶段、不自动处理另一个不相干记录。

## 4. 用户固定表之前仍缺的最小信息

- 哪个字段写“未完成”、哪个是**原始对标视频附件**、哪个是**成品多附件列**；表里的完成标记如何填写（如不允许改状态就只上传并报告）。
- 默认每次只处理一条记录；只有用户另有明确指令才调整。阶段字段不再是前置条件。

**这些信息未绑定前只做只读核查，不从聊天索取原始视频，也不写未知飞书记录。**首次真实流程须在用户指定/批准的记录上验证下载→处理→全部交付文件上传→远端读回后才报告可生产使用。
